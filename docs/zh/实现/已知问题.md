# 已知问题及其来源

## 一、线程

### 1. 一个模块的同步代码会让全部活动暂停

现象：

- 某段同步代码执行的每一毫秒里，其余全部模块、核心的事件转发、配置监听、日志落盘都停止推进
- 代码结束后一切自动恢复，过程中没有任何报错或日志
- 一个模块内 3 秒的同步循环，使包括周期性活动在内的全部活动暂停约 3 秒

来源：

- 所有模块与核心共用同一个线程，模块之间没有线程级隔离
- 任何一段代码不交出线程，其余代码不能运行

## 二、启动

### 2. 启动函数不返回时，该模块永远无法进入运行状态

现象：

- start() 内部的等待没有结束时，模块状态停留在“停止”，不会变成“运行”
- 未声明启动超时时核心无限等待
- 触发这次启动的那次事件派发也随之挂起，调用方拿不到返回
- 已经通过它启动的其他模块不受影响

来源：

- 核心在启动路径上直接等待模块的启动函数返回
- “运行”状态在启动函数返回之后才写入
- JS 无法终止一个已在运行的函数

### 3. 配置了启动超时的模块，超时一次后就不再被事件自动唤醒

现象：

- 声明了 startTimeoutMs（或宿主配置了默认超时）的模块超过期限未完成启动，记一条 module-start-timeout 日志、标记为失败
- 此后即使它的启动事件再次出现，也只会跳过并记一条跳过日志，直到手动启动或配置更新

来源：

- 放弃等待后，原来那个启动函数仍在后台运行，JS 无法终止它
- 若允许事件反复重试，每次都会再堆积一个悬挂调用，因此超时后锁定了自动重试

## 三、停止

### 4.（已修复）关闭过程曾串行，现改为并行等待加超时强制关闭

现象（旧行为）：

- 任何一个模块的 stop() 未返回，排在它后面的模块的停止、公共对象清理、日志收尾都要等它
- 一个故意等待 3 秒的模块把关机从毫秒级拖到 3 秒

修复：

- 停机改为并行调用全部模块的 stop()，总时长等于最慢模块
- 核心等待全部返回“已关闭”，超过 stopTimeoutMs（默认 20s）强制关闭并在 error 日志点名未返回的模块

来源（旧行为）：

- 旧的关闭序列按启动的相反顺序逐个等待各模块停止完成
- 现在等待有全局上限，不再无限挂起

### 5. 核心开始关闭后，新的事件与定向消息均抛错

现象：

- stop() 开始到结束之间，模块或宿主调用发送接口会收到“正在关闭”的异常
- 没接住这个异常的调用点会在关机阶段集中抛出错误

来源：

- 停机期间路由面被整体冻结，用于堵住停机途中模块被复活、新配置被加载的竞态

## 四、事件

### 6. 同一事件的监听者排队转发，前面不返回后面收不到

现象：

- 同一事件有多个监听者时按加载顺序逐个投递
- 排在前面的监听者的处理函数未返回期间，排在后面的监听者收不到这一条事件
- 前面返回后，核心会把这条事件继续送给后面的监听者（延迟补送），延迟时长等于前面处理函数的耗时
- 若前面的处理函数永远不返回，后面的监听者永远收不到这类事件

来源：

- 事件转发按加载顺序逐个等待完成，投递顺序确定

### 7. 没人接住的 Promise 拒绝会杀死整个进程

现象：

- 模块发起一个异步操作、失败后没有任何地方接住这个失败，整个进程立即退出（退出码 1）
- 核心的错误日志里没有这条记录
- 其他模块全部一起终止

来源：

- 核心的错误隔离只包住它自己调用的钩子（事件转发、启动、停止、指令执行等）
- 模块私下发起的异步操作不经过这些包裹，直接落入 Node 对未处理拒绝的默认行为
- 宿主可通过 guardProcess 选项把默认行为改为仅记日志

### 8.（已修复）生命周期同名事件可以被伪造并触发其他模块的反应

现象（旧行为）：

- 模块 A 发出名为 core:startup 的事件，所有以该名字为启动条件的已停止模块会被重新启动，以它为初始化条件的逻辑会再次执行，即使这件事发生在核心关闭途中

修复：

- 事件名改为两段式（来源:事件名），来源段由核心按调用方自动拼装
- 模块发出的任何事件其来源段都是模块自身名字，拼装结果不再是 core:startup，无法命中生命周期事件

来源（旧行为）：

- 旧实现中事件匹配只比较事件名，来源不参与比对

### 9. 请求-应答式的消息链可能成倍增殖

现象：

- 两个模块互相应答、且每次应答又派生新请求时，消息量按 2 的幂次翻倍，全部被如实执行

来源：

- 事件与定向消息的派发没有速率限制和深度上限，每条到达的消息都被完整处理

## 五、日志

### 10. 写入很大的数据会按比例放大日志文件与内存占用

现象：

- 单条日志携带 512KB 数据时，这 512KB 会完整进入落盘文件与内存副本
- 文件更快达到 128KB 轮转线，内存窗口里也被同样的大块内容占据

来源：

- 存储层不做截断
- 内存中保留最近 20000 条的完整内容

### 11. 高频写日志会把更早的条目挤出内存窗口

现象：

- 日志频率高于淘汰速度时，内存里只剩最近 20000 条，更早的记录只能去落盘文件里找

来源：

- 内存窗口容量固定，超出即淘汰最旧的条目
- 落盘文件不受影响

## 六、共享对象

### 12. 拥有者停止或重启时，对象立即从名字上消失

现象：

- 拥有者的 stop() 执行完毕的那一刻，其他人再调用 object(name) 会得到报错
- 此前已经拿到引用的代码仍能操作原来的对象，只是新代码按名字找不到了
- 热加载重启拥有者也会经历同样的消失与重建

来源：

- 对象映射的生命周期绑定在拥有者上，拥有者消失即注销映射

### 13. 对象内容可以无界增长，且不持久化

现象：

- 只 push 不清理的对象会一直占内存
- 核心关闭或拥有者停止后内容直接丢失

来源：

- 公共对象是普通对象引用：没有容量限制，也没有落盘机制

### 14. 对他人的对象执行管理操作会得到报错

现象：

- 对不是自己公开的名字调用 exposeObject 或 unexposeObject 会抛出“已存在/不存在/无权”类错误
- 读写内容不受此限制

来源：

- 管理操作校验拥有者身份，只有拥有者本人能公开或取消公开

## 七、配置

### 15. YAML 变坏后每轮重复一条相同错误，恢复前模块停在旧配置

现象：

- 某个已存在模块的 YAML 变得无法解析（清空、截断、格式错误），模块保持运行，用的是最后一份成功解析的配置
- 此后每轮扫描（默认 200ms）都重读这个坏文件、再记一条相同的 error，直到文件恢复为止
- 恢复后模块按新配置热更新（索引即时刷新，实例不动）

来源：

- 解析失败的文件不更新指纹，导致下一轮继续重试
- 模块槽位只在文件被删除时移除，解析失败不触发移除

### 16. 直接覆盖写入 YAML 存在被读到半个文件的窗口

现象：

- 用一次性覆写的方式更新配置时，监听器可能在写到一半的时刻读取磁盘，读到残缺内容
- 后果与上一条相同：报错重试，应用的是旧配置，直到写入完成并成功解析

来源：

- 监听器按固定间隔读取磁盘上的当前字节，不感知任何写入过程

### 17.（已修复）配置变化曾会重启对应模块，现改为 YAML 层热生效

现象（旧行为）：

- 哪怕只改了一行注释，该模块也会经历完整的停止、重新加载程序、重新启动
- 模块变量里积累的状态全部丢失

修复：

- YAML 更新只重载 YAML 本身（配置、监听声明、匹配索引），运行中的模块实例与代码不动
- 模块通过 ctx.config 读取新配置、自行决定何时应用
- 代码重载由模块自己发起（ctx.requestReload）

来源（旧行为）：

- 删除 require 缓存、重新加载程序并重跑整个生命周期

## 八、定向消息

### 18. sendTo 返回 true 不代表对方处理成功

现象：

- 对方存在且实现了接收接口时即返回 true，即使对方的处理函数当场抛错
- 调用方无法从返回值区分“处理成功”与“对方处理失败”，后者只进错误日志

来源：

- 送达规则定义为“存在可接收方即算送达”，处理结果不回传给调用方

### 19. 忘记实现 onMessage 的模块收不到任何定向消息，且没有任何提示

现象：

- 发送方拿到返回值 false，除此之外没有其他信号表明“目标是因为没实现接口而收不到”

来源：

- 定向消息采用显式订阅设计：不实现 onMessage 即视为不订阅

## 九、进程边界

### 20. 模块之间没有权限控制

现象：

- 任何模块都可以向核心发出管理指令：启动或停止其他模块、生成任意事件
- 任何模块都可以读写全部公共对象的内容

来源：

- 信任模型为“安装即信任”：管理面对所有模块开放
- 全部代码在同一进程内，权限检查无法强制执行
