# 场景：停机协议

宿主调用 core.stop() 关闭整个软件。

## 流程

1. 守卫：未启动或已在停机直接返回；置 stoppingFlag。
2. 停止配置监听，冻结文件面。
3. 遍历模块：已停止与失败的跳过；starting 的作废启动（代数递增、置 stopped、注销数组）；running 的生成关闭任务。
5. 关闭任务并行执行：调用 stop()，返回即已关闭，抛错仅记 error；置 stopped、注销公开数组、记 module-stop。
6. 等待全部关闭任务完成，超过 stopTimeoutMs 强制关闭并在 error 日志点名未返回的模块。
7. 注销核心自身数组，复位标志，记 core-stop，关闭日志文件。

## 边界

- 悬挂模块（stop 永不返回）无法被终止：超时只是不再等待，其状态保持 running，数组未注销（见 已知问题 4）。
- 超时边界竞态可能误点名刚返回的模块。
- stop 钩子抛错被吞：宿主无法用 await stop() 的拒绝感知失败，只有日志。
- 停机期间模块调用发送接口抛错（见 已知问题 5）。
- 单个悬挂模块拖住整个停机默认 20 秒（见 已知问题 4）。
- starting 模块的启动被作废，靠核心事后回收。
- 停机窗口内的文件变更被静默吞掉，无日志。
- 日志文件关闭不是硬密封：悬挂模块事后返回会重新打开流继续写。
- 停机后同一实例再 start() 不清场，旧槽位残留。
